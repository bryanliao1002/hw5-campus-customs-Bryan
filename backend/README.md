# Campus Customs agent backend

This package defines the five PydanticAI roles, their typed output contracts, and the bounded all-to-all coordinator. `backend/orchestrator.py` provides `resolve_open_tickets()`, which restores `data/campus_customs_new.db` from the untouched original by default, launches the existing MCP server over stdio, and asks Boss to review the open queue. It is safe to import the package; the reset/model workflow runs only when the function is explicitly called (or this module is run as a script).

Create an isolated backend environment and install its requirements:

```sh
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.txt
backend/.venv/bin/python -m backend.orchestrator
```

The MCP child process uses `mcp_server/.venv/bin/python` when available; otherwise it uses the active backend Python, which has the MCP 1.x requirement. Set `PORTKEY_API_KEY` in the environment or in the root `.env` before running. The single configured model is `gpt-6-luna` at Portkey; there is no direct-provider or alternate-model fallback. Running the module resets the working database from the original, then makes live Portkey requests and starts ticket resolution.

Agents access business data and perform ticket-board writes only through the shared MCP tools. Delegation is available to any other role and is bounded by call, depth, request, tool-call, and token limits documented in `output/harness.md`. The agent tools can add a draft or queue a payment for human approval, but cannot send communications, approve, or process payments. Every agent turn and MCP interaction is appended to `output/audit_trail.json`.

Each agent invocation permits up to 8 model requests, 12 MCP/delegation tool calls, and 14,000 total tokens, within the unchanged shared 24,000-token workflow budget. The per-agent cap was raised modestly after an audited Boss synthesis used 13,531 tokens while the whole workflow remained within its shared allowance. Ticket-specific routing now avoids redundant Inventory work and repeated product lookups for Ticket 103; this is the first control, with the modest per-agent headroom as a bounded backstop. Each invocation also caps cumulative generated output at 2,400 tokens. Nested accounting charges each invocation's token deltas once; before delegation it accounts the parent's current usage, then reduces the parent's remaining total-token allowance when the child returns. A 1,200-token reserve protects the parent's next synthesis turn, and the parent is stopped before another request if the reserve is exhausted. Failed invocations retain observed request/tool/token usage in the audit and charge consumed tokens to the workflow budget. Runs are not automatically retried after errors because an earlier turn may have safely queued a proposal or saved a draft; inspect activity and MCP state before manually restarting a failed ticket.

The FastAPI dashboard app is `backend/main.py`. From the `backend/` directory, run `uvicorn main:app --reload --port 8000`; the default loopback server is available at `http://localhost:8000` and interactive API docs at `/docs`. It exposes ticket status/run, run polling, recent audit activity, payment/purchase approval and rejection, operational decision review, checking balance, and database reset routes documented in `output/harness.md`. Financial and operational decision routes are local-only. The isolated human-approval MCP process is never included in any agent toolset.

Tickets 101 and 103 support an explicit Boss-only recovery when the latest workflow failed specifically during Boss synthesis from a token-limit error. `GET /api/tickets/{ticket_id}/recovery-candidate` reports audit-only candidacy; the dashboard submits the exact failed workflow ID to `POST /api/tickets/{ticket_id}/recover-synthesis`. FastAPI checks the saved specialist outputs and fresh MCP evidence before queueing and the worker repeats those checks immediately before Boss runs. Ticket 103 requires its Accounting and Customer Service reports, their audited successful writes matched to `get_ticket_board_items`, current product/pricing facts, the single decided target-price choice, no unresolved approvals, and an open ticket. Boss receives compact evidence without tools/delegation (3,000 total tokens, 700 output tokens, two requests for Ticket 103); completed specialists are not rerun and no decision, payment, or board item is rewritten. The original failed run remains in the audit; recovery creates its own workflow record. It does not set ticket status itself: Boss must synthesize truthfully, then the normal MCP final-disposition gate must pass. MCP rejects agent-time status changes, preventing premature `mark_ticket_resolved` calls. Missing, duplicate, corrupt, or stale evidence is rejected before the model call. Tests use disposable database/decision/audit copies and PydanticAI `TestModel` through MCP stdio—not paid Portkey calls.

After a human-approved payment is recorded, FastAPI does not relaunch agents automatically. The dashboard offers explicit continuation only when the latest `needs_human` workflow's own request is processed and matches a payment ledger record. Ticket completion is gated by the MCP final-disposition function: the latest workflow must have completed, all financial proposals need a human outcome, and an out-of-stock customer order needs a decided human fulfillment decision with terms. `request_human_decision` and `list_decisions` use a file-locked JSON store outside the shop database; the human-only `record_human_decision` tool is only in the isolated approval MCP process. A decision request is idempotent per ticket and kind: an existing pending or decided record is returned on retry, so it cannot be duplicated or replaced. Recording a decision does not itself change ticket status; FastAPI asks MCP to re-evaluate the final disposition afterward. For Ticket 101, paying invoice 501 alone leaves it open while size-S stock is unavailable and no human fulfillment choice is recorded.

For an out-of-stock order, “resolved” means the blocking issue was handled and a human explicitly selected the fulfillment outcome; it does **not** mean the item was delivered. No goods-receipt tool is currently implemented. A future human-only `receive_purchase_order` capability should record actual received quantity against an approved PO and transactionally update inventory, owned by Inventory with Accounting reconciling.

The HW5 backend uses the assignment port `8000`; the React dashboard runs on `5173` and is included in the backend's CORS allowlist.
