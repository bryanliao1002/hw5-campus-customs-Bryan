# Campus Customs MCP Server

The standard FastMCP server is the agents' sole interface to shop records. It connects to **`data/campus_customs_new.db`**, never to the protected original `data/campus_customs.db`. Read tools are read-only against business records; write tools can save ticket-board items or queue payment/purchase proposals. Agents cannot approve or process payments, send messages, or contact vendors.

Install the MCP SDK 1.x environment used by the Codex MCP configuration:

```sh
python3 -m venv mcp_server/.venv
mcp_server/.venv/bin/python -m pip install -r mcp_server/requirements.txt
```

Start manually from the project root with `mcp_server/.venv/bin/python mcp_server/server.py`. The agent backend starts the same server over stdio with PydanticAI. All tool invocations, inputs, results, and errors are appended to `output/audit_trail.json`; no API credentials are passed to or logged by this server.

## Available tools

| Tool | Database tables used | Purpose / safety behavior |
|---|---|---|
| `get_ticket_product_context(ticket_id)` | `tickets`, `inventory`, `pricing` | Reports the ticket's SKU/size, requested and available quantities, shortfall, location, unit cost, and list price. Useful for ticket 101's unavailable size-S tee and ticket 103's 12-hoodie shortfall and discount arithmetic. |
| `get_ticket_supplier_context(ticket_id)` | `tickets`, `invoices`, `vendors`, `desk` | Follows a ticket-linked invoice to its vendor, uses `vendors.lead_days`, checks all unpaid invoices for that vendor, and evaluates overdue status against `desk.date_today`. For ticket 101, the open invoice blocks further shipment from Bulldog Print Co. |
| `get_ticket_rent_context(ticket_id)` | `tickets`, `leases`, `desk` | Reads the linked lease and compares its due date with the shop's stored business date. Ticket 102's $2,400 rent is due two days after 2026-08-31, not overdue. |
| `list_open_tickets()` | `tickets` | Returns the open work queue for Boss to triage and includes the ticket IDs, request details, and status. |
| `list_tickets()` | `tickets` | Returns all tickets and statuses for the dashboard to show open versus resolved work. |
| `get_cash_balance(account_name="checking")` | `cash_accounts` | Returns the current balance and recorded balance date for the dashboard. |
| `list_pending_approval_requests()` | `payment_requests`, `purchase_requests`, `tickets`, `vendors` (when extension tables exist), `sqlite_master` | Shows pending requests in a dashboard-friendly format; it does not approve them. |
| `request_human_decision(ticket_id, kind, question, recommendation, options)` | `tickets`; external file-locked `output/human_decisions.json` | Adds one pending operational decision (`fulfillment`, `discount`, or `other`) per ticket/kind. Retries return the existing pending or decided record rather than duplicating or replacing it; ticket status is unchanged. |
| `list_decisions(ticket_id=None, status=None)` | External `output/human_decisions.json` | Read-only view of pending/decided human choices, approver identity, terms, and UTC timestamps. |
| `get_ticket_financial_context(ticket_id)` | `tickets`, `cash_accounts`, `payments`, `invoices`, `leases`, `payment_requests`, `purchase_requests` (when initialized), `desk`, `sqlite_master` | Supplies current cash balances, recorded outgoing payments, linked obligation details, shop date, and pending payment/purchase requests. The current account balance is authoritative; don't add revenue. |
| `get_ticket_restock_options(ticket_id)` | `tickets`, `inventory`, `vendors`, `invoices` | Reports available stock and every recorded vendor's actual specialty and lead time, with unpaid invoices and shipment eligibility. It also returns the ticket-linked invoice facts (including its description and vendor ID) when present; this can identify historical sourcing, but the schema has no SKU/vendor mapping and current supply remains unconfirmed for human review. |
| `append_ticket_board_item(ticket_id, item_type, body, author)` | `tickets`, `ticket_updates` | Appends an internal note or a labeled customer/vendor message draft to the ticket board. It never sends external communication. Supported item types are `agent_note`, `customer_message_draft`, and `vendor_message_draft`. |
| `get_ticket_board_items(ticket_id)` | `tickets`, `ticket_updates` (if initialized) | Read-only access to saved notes and drafts with stable update IDs. The recovery path uses it to verify existing Ticket 103 specialist work instead of writing duplicate board items. |
| `request_payment_approval(ticket_id, kind, ref_id, amount, account)` | `tickets`, `invoices` or `leases`, `cash_accounts`, `payments`, `payment_requests`, `purchase_requests` | Validates an exact ticket-linked invoice/rent amount, account, existing payments, and available funds, reserves cash across payment and purchase proposals, then stores status `pending_approval`. It cannot approve or execute the payment and rejects insufficient funds. |
| `request_purchase_approval(ticket_id, vendor_id, qty, account="checking")` | `tickets`, `inventory`, `pricing`, `vendors`, `invoices`, `cash_accounts`, `payment_requests`, `purchase_requests` | Queues an exact shortfall proposal at the recorded unit cost. It rejects suppliers with unpaid invoices and insufficient funds, reserves the proposed amount, flags the SKU/vendor match as unconfirmed, and does not place an order. Human approval must confirm vendor capability. |
| `mark_ticket_resolved(ticket_id, resolution_note)` | `tickets`, `inventory`, `invoices`, `leases`, `payments`, `payment_requests`, `purchase_requests`, `ticket_updates`, `pricing`; external workflow audit/decision JSON | One documented final-disposition gate requires the latest ticket workflow to have completed and every payment/purchase proposal to have a human outcome. A customer order needs its linked invoice paid; if exact stock is short, it also needs a decided human fulfillment choice with terms. It never consumes or increases inventory. An out-of-stock order marked resolved means its blocker was handled and a human explicitly chose an outcome—not that the item was delivered. Rent and price-override evidence rules remain in force. |

## Human-only tools (isolated approval MCP)

| Tool | Tables / records | Purpose |
|---|---|---|
| `approve_and_process(request_type, request_id, approved_by, confirm_vendor_can_supply=false)` | `payment_requests` or `purchase_requests`, `invoices` or `leases`, `cash_accounts`, `payments`, plus validation tables | Requires an explicit human approver; processes an eligible request transactionally with duplicate-payment and nonnegative-cash checks. Purchase approval confirms supplier capability but does not record goods received. |
| `reject_financial_request(request_type, request_id, rejected_by, reason)` | `payment_requests` or `purchase_requests`; audit trail | Records the human's rejection reason, releases the pending reservation, and changes no cash balance. |
| `record_human_decision(decision_id, decided_by, choice, terms)` | External `output/human_decisions.json` and audit trail | Records a known pending operational choice with current UTC time; cannot be backdated or re-decided and does not itself change ticket status. |

This isolated process is called only by local human-controlled FastAPI routes; these tools are not listed in any agent's MCP toolset.

`ticket_updates`, `payment_requests`, and `purchase_requests` are application-owned tables created on the first relevant write in the working database. Human operational decisions live in the separate file-locked `output/human_decisions.json`; no shop-database table or column is added for them. The isolated `approval_server.py` exposes `approve_and_process`, `reject_financial_request`, and `record_human_decision`; none is attached to agent toolsets. Payment approval rechecks obligations, supplier holds, pending cash reservations, and balance transactionally before recording payment and reducing cash. Rejection records the human reviewer/reason and moves no cash. Purchases are only financial proposals; approval requires a human's exact-item supplier confirmation and does not record receipt. No tool sends a purchase order or external communication.

For an out-of-stock order, “resolved” means its blocking issue was handled and a human explicitly decided the fulfillment outcome (for example defer, backorder, or cancel). It does **not** mean the item was delivered. The current team cannot record an actual shipment receipt; a future human-only `receive_purchase_order` tool should record received quantity against an approved PO and update inventory transactionally, owned by Inventory with Accounting reconciling. That capability is intentionally not implemented.

Payment requests accept only `kind="invoice"` or `kind="rent"`. An obligation with any existing proposal or recorded payment cannot be requested again. Human approval does not automatically resume agents: the dashboard may offer an explicit continuation only after FastAPI verifies the prior `needs_human` run's request is processed and matches a recorded payment. `mark_ticket_resolved` is the only status-changing MCP tool; calls made while an agent is active are rejected, and FastAPI invokes the evidence gate after workflow completion.

The backend offers a narrow Boss-synthesis recovery for Tickets 101 and 103 only when the latest workflow failed due to Boss's token limit and required specialist outputs are persisted. Ticket 103 additionally verifies the exact Accounting and Customer Service MCP writes against current ticket-board records, current stock/pricing, the single decided target-price choice, and the absence of unresolved financial or human decisions. `get_ticket_board_items` supports that read-only verification. Recovery gives a compact evidence packet to Boss alone (no MCP tools or delegation), with a 3,000-token, 700-output-token, two-request cap for Ticket 103. It appends a separate recovery workflow and does not erase or rewrite the failed source run. No payment, decision, or board item is repeated. Boss must complete synthesis, then FastAPI invokes `mark_ticket_resolved` through MCP and the standard final-disposition rules still apply. The dashboard exposes this only as an explicit local action; missing, duplicate, or stale evidence fails closed before Boss is called.
